## 1. 你们在做什么(5 分钟)

**产品一句话**:用户输入一个公司名,系统去抓这家公司的 ESG(环境)页面、搜相关新闻,让 AI 按 5 个维度打"漂绿风险分",最后生成一份带证据、可下载 PDF 的报告。

**三个服务怎么配合**(把这张图画在白板上):

```
 用户浏览器                      A 的地盘                 B 的地盘                  C 的地盘
┌──────────┐   打开网页    ┌──────────────┐  HTTP    ┌──────────────┐  HTTP   ┌──────────────┐
│  Chrome   │ ───────────▶ │  frontend/    │ ───────▶ │  backend/     │ ──────▶ │  analysis/    │
│           │              │  React 网页    │  /api/* │  FastAPI      │  /run   │  FastAPI      │
└──────────┘              │  (Vercel 部署) │ ◀─────── │  (Railway)    │ ◀────── │  (Railway)    │
                           └──────────────┘  JSON    └──────┬───────┘  写结果  └──────┬───────┘
                                                            │      ┌────────────┐     │
                                                            └────▶ │  Supabase   │ ◀───┘
                                                              读    │  (数据库)   │  写
                                                                   └────────────┘
```

- **A(前端)**:用户看到的一切。网页发请求给 B,把 B 返回的 JSON 画成报告。
- **B(后端)**:收前端请求、管数据库、把 C 算好的结果整理成前端要的形状、生成 PDF。
- **C(分析)**:真正干活的:抓网页、搜新闻、调 AI、算分,把结果写进数据库。

**为什么拆三块**:AI 分析要 30–60 秒,网页不能干等;所以 B 先回一句"收到,单号 job_id",前端每 3 秒问一次"好了没"(这叫**轮询 polling**),C 在后台慢慢算。三个人也因此可以**各管一个文件夹,互不踩脚**。

## 4. Git 三人协作:不打架的最小流程(全队一起操作,约 20 分钟)

**先建仓库**:一人(建议 B)在 GitHub 上 New repository(名字如 `greencheck`,Private),把另外两人加为 Collaborator(仓库 Settings → Collaborators)。

**每人把仓库拉到本地**:
```bash
# 在你想放项目的地方(比如桌面)打开终端
git clone https://github.com/你们的用户名/greencheck.git
cd greencheck
git config user.name "你的名字"
git config user.email "你的GitHub邮箱"
```

**黄金法则(贴墙上)**:
1. **A 只改 `frontend/`,B 只改 `backend/`,C 只改 `analysis/`** —— 目录即领土。遵守这条,你们三周内几乎不会遇到合并冲突。
2. 想改别人目录?**喊人,让领主自己改**,或开个 PR 让领主审。
3. `main` 分支永远是"能跑的版本"。日常工作在自己的分支上。

**每天的循环(背下来,就这 6 步)**:
```bash
git checkout main && git pull          # ① 早上:回到主干,拉最新
git checkout -b feat/a-landing        # ② 开今天的分支(命名:feat/你的字母-在做什么)
# ……写代码……
git add .                              # ③ 把改动放进"待提交篮子"
git commit -m "feat(a): landing 三个输入Tab"   # ④ 提交(描述写人话)
git push -u origin feat/a-landing      # ⑤ 推到 GitHub
# ⑥ 到 GitHub 网页上点 "Compare & pull request" → 在群里喊一声 → 自己点 Merge
```

> **新手 FAQ**:
> - *commit 和 push 什么区别?* commit 是存档在你电脑,push 是上传到 GitHub 给队友看见。
> - *什么时候 merge?* 本手册的节奏是:**每完成一个 Phase 就 merge 一次**。小步快跑,谁也不会落后主干太远。
> - *真冲突了怎么办?* 终端会提示 `CONFLICT`。别慌:用 VS Code 打开冲突文件,它会显示「Accept Current / Incoming」按钮,和对方一起看着选,选完 `git add . && git commit` 即可。遵守黄金法则①,这事一学期遇不到两次。

## 7. 卡住了怎么自救(背下来这四步)

1. **读报错的最后 3 行**。Python 报错从下往上读,最后一行是病名(如 `ModuleNotFoundError: No module named 'fastapi'` = 没装包/没进虚拟环境);前端看浏览器 Console(F12)红字。
2. **把病名原样搜一下**(报错信息 + 包名)。90% 的坑前人踩过。
3. **对照参考实现**的同名文件,用肉眼 diff。
4. **问队友,用这个模板**(能让对方 30 秒进入状况):
   > 我在做【手册 X 册 Phase N 第几步】,敲了【命令/代码】,期望看到【…】,实际看到【贴报错最后3行】,我已经试过【…】。

常见病速查:

| 症状 | 病因 | 药 |
|------|------|----|
| `command not found: npm/python3` | 没装 / 没加 PATH | 回第 2 节重装,装完**重开终端** |
| `ModuleNotFoundError` | 没激活虚拟环境就跑 | `source venv/bin/activate`(看到命令行前面出现 `(venv)` 才算进去了) |
| `EADDRINUSE` / `address already in use` | 端口被占(上次的服务没关) | 关掉旧终端;或换端口 |
| 前端请求 `/api` 报 404/CORS | 后端没起 / 代理没配 | 确认 8000 端口活着;查 `vite.config.js` 代理段 |
| `.env` 改了不生效 | 服务没重启 | Ctrl+C 停掉,重新跑启动命令 |
| push 被拒 `rejected` | 远端比你新 | `git pull` 再 push |
